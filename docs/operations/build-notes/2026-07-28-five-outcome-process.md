# Build Note · 2026-07-28 · Five-Outcome Development System

- Change class: `R`
- Related decision: ADR-0005

## Outcome

Converted the project owner's AI Coding, Agent Engineering, production, career and wealth goals into
repository-documented workflows and project defaults for development, learning, interviews and business.

## Why this matters

The previous foundation could guide architecture but did not prevent infrastructure drift or prove that the
owner was learning. Future work now has explicit outcome alignment, mastery evidence, TDD routing, Codex
delegation rules and market gates.

## Evidence

- Five-Outcome Charter, Curriculum, Capability Matrix and weekly/monthly Scorecard;
- risk-proportional TDD with exclusive S / Task Brief / ExecPlan / Spike routing;
- Codex Playbook, project config and three read-oriented custom Agent roles;
- phase-gated Roadmap and a living Stage 1 ExecPlan;
- Business Validation Roadmap and Interview Evidence Pack;
- updated AGENTS, contribution, PR and Build Note templates.
- verification: 17 Java tests, 4 JSON Schemas with 8 fixtures, 1 synthetic Eval Task Pack,
  50 Markdown link checks, 4 TOML files and 6 GitHub YAML files passed;
- three independent read-only reviews were used for process consistency, roadmap realism and Codex
  configuration; P0/P1 repository findings were corrected before commit.

## Failure and limits

- Documents and configuration do not prove that the process will improve delivery.
- Human mastery remains unassessed until teach-back, transfer and debugging exercises are performed.
- ICP, retention, willingness to pay and price remain hypotheses.
- Custom Agent usefulness must be measured; they should be removed if coordination cost exceeds value.
- There is no historical cycle-time or escaped-defect baseline, so this change does not claim that the
  process has made development faster.

## Principle learned

AI Coding maturity is not how much code an Agent can write. It is the ability to frame, delegate, verify,
debug and retain ownership while converting real user problems into reliable outcomes.

## Next falsifiable hypothesis

Across Stage 1, record per-slice start/end time, Agent count, accepted/rejected findings, collision/rework and
escaped defects. After repeated slices, test whether the protocol deserves to be simplified, retained or
strengthened; do not infer causality from one run. In parallel, test whether the owner can reach L3 on two
mechanisms and whether Concierge delivery obtains real reuse/price evidence.

- Business: no new user or payment evidence in this slice.
